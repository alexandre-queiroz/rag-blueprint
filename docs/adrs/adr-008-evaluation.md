# ADR-008: Evaluation Framework — RAGAS

- **Status:** Accepted
- **Date:** 2026-05-27
- **Author(s):** Alexandre Queiroz
- **Version:** 1.0

---

## Context

A RAG system can work technically — receive queries, fetch chunks, call the LLM, return a response — and still deliver poor answers. Failure modes are subtle: the model may ignore the retrieved context and hallucinate, the retrieved chunks may be irrelevant, or the response may not actually answer the question.

To detect these problems, the system needs evaluation at two distinct moments (FR-03, FR-11):

1. **Offline:** before any deploy, against a fixed dataset of questions and expected answers — ensures that a chunking or embedding change did not degrade retrieval
2. **Online:** continuously in production, sampling a fraction of real traffic — detects degradation over time without depending on a fixed dataset

The metrics that matter for a RAG:
- **Faithfulness:** is the response grounded in the retrieved context? (detects hallucination)
- **Answer relevancy:** does the response actually answer the question?
- **Context precision:** were the retrieved chunks the relevant ones for answering?

---

## Decision

Use **RAGAS** as the evaluation framework, for both offline evaluation and online sampling in production.

---

## Rationale

- Most recognized framework in the RAG evaluation ecosystem — consolidated documentation and active community reduce edge case surprises in implementation
- Covers exactly the three metrics that matter for this system (faithfulness, answer relevancy, context precision)
- Using the same framework offline and online keeps metrics comparable — a drop in production is directly comparable to the offline baseline
- Since embeddings are generated by Chroma Cloud (server-side), RAGAS evaluates the quality of chunks already retrieved by hybrid search — `context_precision` indirectly captures retrieval quality without needing to access the embedding model

---

## Alternatives Considered

### Alternative A — DeepEval

Evaluation framework with broader metric coverage and assertion-style API.

**Perceived advantages:**
- More metrics available out-of-the-box
- pytest-style API facilitates CI pipeline integration

**Reasons to reject:**
- Lower adoption than RAGAS — less reference material and community-documented use cases
- The additional metrics are not needed for this system's scope

### Alternative B — Custom implementation

Write the evaluation metrics from scratch.

**Perceived advantages:**
- Full control over what is measured and how
- Zero dependency on an external framework

**Reasons to reject:**
- High maintenance cost — RAG metrics (especially faithfulness with LLM judge) have non-trivial edge cases
- Reinvents solutions that RAGAS already has validated
- Diverts project focus from architecture to evaluation engineering

---

## Consequences

**Expected benefits:**
- Detection of quality regressions before they reach the user (offline)
- Continuous quality monitoring without a fixed dataset (online, via sampling)
- Comparable baseline between offline and production

**Trade-offs and accepted risks:**
- Some RAGAS metrics use an LLM as judge internally — adds evaluation cost per sampled request in production
- `sample_rate: 0.10` (10% of traffic) and `min_score_threshold: 0.75` are starting points — both need to be calibrated with real data before being used as alert triggers

**Required actions:**
- Online evaluation must run asynchronously — must not block the response to the caller
- Install evaluation dependencies separately: `uv sync --extra eval`
- Create an offline Q&A dataset for pre-deploy evaluation
- Configure alerting pipeline when metrics fall below `min_score_threshold`

**Triggers for reassessment:**
- `context_precision` consistently below threshold → escalation: add cross-encoder reranker after hybrid search (see ADR-002)
- LLM judge cost in production exceeding the benefit of monitoring → reduce `sample_rate` or switch to metrics without LLM judge (e.g. BERTScore)
- RAGAS ceasing active maintenance
